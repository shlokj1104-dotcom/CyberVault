## Key Insight of the Day

**Python:** Tuples, dicts, and sets each solve a specific problem that lists can't: a dict gives you O(1) lookup by name instead of position; a tuple gives you an immutable record that can be hashed and used as a key; a set gives you O(1) membership testing and deduplication in one step. The DSU pattern is particularly elegant — by stuffing a computed key into position 0 of a tuple, you hijack Python's default lexicographic sort to sort by anything you want, with zero extra syntax.

**Networking:** The most striking thing about Section 1.6 is that none of the four attacks require inventing anything new. Malware spreads because the network was designed to deliver arbitrary data. Sniffing works because broadcast media don't discriminate. IP spoofing works because routers only ever read the destination address. DoS works because finite buffers and bandwidth were always a known design constraint. Every attack is just the honest design of the Internet, used in bad faith. The defenses — encryption, ingress filtering, end-point authentication — are all things that had to be retrofitted on top of an architecture that never anticipated needing them.

## Problems I Encountered

### Python — Lists

**Confusion #1: `sort()` returns `None`** **Problem:** Tried `t = t.sort()` — `t` became `None` and all data was lost. **Resolution:** `sort()` modifies in place and returns `None`. Never assign it. Use `sorted(t)` if you need a new sorted list to assign.

**Confusion #2: `b = a` creates an alias, not a copy** **Problem:** Modified `b`, then saw `a` had changed too. **Resolution:** `b = a` makes both names point to the same object. Use `b = a[:]` for an independent copy. This is the same aliasing issue as string variables but more dangerous because lists are mutable.

**Confusion #3: `remove()` only deletes the first occurrence** **Problem:** Had a list with duplicate values, called `remove()`, expected all copies gone. **Resolution:** `remove()` finds and removes only the first match. To remove all occurrences, use a `while` loop: `while 'x' in t: t.remove('x')`.

### Python — Dictionaries

**Confusion #4: `d[key]` vs `d.get(key)`** **Problem:** Kept getting `KeyError` when accessing keys that might not exist yet (counter pattern). **Resolution:** Use `d.get(key, 0)` whenever the key might be absent. Use `d[key]` only when you're certain the key exists. The counter pattern is specifically `d[c] = d.get(c, 0) + 1`.

**Confusion #5: Modifying a dict while looping over it** **Problem:** `RuntimeError: dictionary changed size during iteration` when adding/removing keys inside a `for k in d:` loop. **Resolution:** Loop over a copy of the keys: `for k in list(d.keys()):`. This creates a static snapshot to iterate over while modifying the original.

**Confusion #6: How deep should nesting go?** **Problem:** Started building a dict inside a dict inside a dict — rapidly became unreadable. **Resolution:** Two levels of nesting is the practical ceiling. If you find yourself going deeper, the data probably belongs in a class or a list of flat dicts with consistent keys.

### Python — Tuples

**Confusion #7: Single-element tuple syntax** **Problem:** `t = (42)` is just an int — the parentheses are ignored. Spent time confused about why `type(t)` said `int`. **Resolution:** The comma makes the tuple, not the parens. `(42,)` is a tuple. `(42)` is an int in brackets. No other Python syntax works this way — it's a genuine gotcha.

**Confusion #8: Why use a tuple as a dict key instead of a string?** **Problem:** Wasn't clear why `directory[('Doe', 'John')]` is better than `directory['Doe_John']`. **Resolution:** Tuples preserve structure. `('Doe', 'John')` can be unpacked — `for last, first in directory:` — without parsing strings. The two components remain individually accessible. String keys would require `.split('_')` and lose type safety.

### Python — Sets

**Confusion #9: `{}` is an empty dict, not an empty set** **Problem:** Wrote `s = {}`, then `s.add('apple')` — `AttributeError: 'dict' object has no attribute 'add'`. **Resolution:** `{}` is hardwired to mean empty dict in Python. Always use `set()` for an empty set. This is a known inconsistency in Python syntax — the price paid for dict literal syntax.

**Confusion #10: Set order is unpredictable** **Problem:** Printed a set and expected alphabetical order — got something arbitrary. **Resolution:** Sets are unordered by design — there is no "position" to maintain. If you need ordered unique elements, convert back to a sorted list: `sorted(my_set)`.

### Networking

**Confusion #11: Bandwidth flooding vs connection flooding — aren't both just "too much traffic"?** **Problem:** Both felt identical — both crash the server. **Resolution:** They attack different resources. Bandwidth flooding fills the _access link_ — the pipe itself. Even if the server is fine, packets can't get through. Connection flooding fills the server's _TCP connection table_ — the server might have plenty of bandwidth but runs out of memory to track half-open connections. Bandwidth flooding is a network problem; connection flooding is a server resource problem.

**Confusion #12: Why can't ISPs just block spoofed packets before they enter the Internet?** **Problem:** Ingress filtering sounds simple — drop packets where source IP doesn't match the network the packet arrived from. Why isn't this universal? **Resolution:** Two reasons. First, ISPs have no incentive to filter traffic that doesn't hurt _their own_ customers — the cost lands on the victim's ISP. Second, ingress filtering requires every single ISP to implement it; one non-compliant ISP is all an attacker needs. This is the same coordination problem that makes many Internet security improvements slow to roll out.

**Confusion #13: Can a packet sniffer on WiFi capture WPA3-encrypted traffic?** **Problem:** WPA3 encrypts the wireless link — does that make sniffing impossible? **Resolution:** WPA3 encrypts the _link layer_ frame — the payload (IP datagram and above) is protected from eavesdroppers on that specific wireless segment. But if the attacker can reach a point upstream of the WiFi (an unencrypted HTTP server, a router tap), sniffing is still viable. WPA3 stops sniffing _on the air_, not end-to-end. TLS/HTTPS protects the content all the way to the server regardless of what the link does.
