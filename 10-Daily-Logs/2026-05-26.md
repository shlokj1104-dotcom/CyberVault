### Networking — Section 2.2: The Web and HTTP

- [x] Web pages as collections of objects: base HTML + referenced images, CSS, JS — each addressable by a single URL (20 min)
- [x] URL structure: hostname + path name; `Host:` header required by HTTP/1.1
- [x] HTTP as request-response protocol: client pulls objects on demand; server maintains no state
- [x] HTTP runs over TCP on port 80 (HTTPS port 443) — reliable delivery required; UDP inappropriate
- [x] Stateless by design: no session tables, no client history; simplicity and scalability over memory

- [x] RTT defined: round-trip time including propagation, queuing, and processing delay
- [x] Response time formula: `2 × RTT + file transmission time` per object; browsers mitigate with 5–10 parallel connections
- [x] Persistent HTTP (HTTP/1.1 default): same TCP connection reused; three-way handshake paid once
- [x] Persistent without pipelining: ~1 RTT per object; persistent with pipelining: ~1 RTT total for all objects
- [x] HTTP request message format: request line (method + URL + version), header lines, blank line, entity body
- [x] Key request headers: `Host:`, `Connection:`, `User-agent:`, `Accept-language:`
- [x] HTTP methods: GET (no body), POST (body), HEAD (headers only), PUT (upload), DELETE (remove)
- [x] GET with forms: data appended to URL after `?`; POST puts data in entity body — never use GET for passwords
- [x] HTTP response message format: status line (version + code + phrase), header lines, blank line, entity body
- [x] Key response headers: `Connection:`, `Date:`, `Server:`, `Last-Modified:`, `Content-Length:`, `Content-Type:`
- [x] Status code categories: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error
- [x] Critical status codes: 200 OK, 301 Moved Permanently, 304 Not Modified, 400 Bad Request, 404 Not Found, 505 Version Not Supported
- [x] Cookies — four components: `Set-cookie:` response header, `Cookie:` request header, browser cookie file, server back-end database
- [x] Cookie lifecycle: first visit → server creates unique ID → `Set-cookie` sent → browser stores it → all subsequent requests carry `Cookie: ID` → server personalises response
- [x] Cookie use cases: session authentication, shopping carts, personalisation, recommendations, third-party tracking
- [x] Cookie privacy concern: cross-site profiles via ad network third-party cookies; GDPR implications
- [x] Web cache / proxy server: stores recently requested objects; simultaneously a server (to browsers) and a client (to origin servers)
- [x] Cache request flow: browser → cache → cache HIT serves locally; MISS fetches from origin, stores copy, forwards to browser
- [x] Quantitative case for caching: 15 Mbps demand on 15 Mbps link → traffic intensity 1.0 → infinite queuing delay; cache with 0.4 hit rate reduces effective load to 0.6 → ~1.2 s average response time at fraction of link upgrade cost
- [x] CDNs: geographically distributed caches; shared CDNs (Akamai, Cloudflare) vs dedicated CDNs (Google, Netflix)
- [x] Conditional GET: `If-Modified-Since:` header carries cached `Last-Modified` date; server replies `304 Not Modified` (empty body) if unchanged, `200 OK` with new body if changed

## Key Insight of the Day

**Python:** The progression from raw sockets → urllib → BeautifulSoup traces the same abstraction ladder as the networking stack itself. At the socket level, you are writing bytes directly into a TCP pipe and parsing the HTTP protocol by hand — every `\r\n\r\n` and `recv(512)` loop is manual. urllib lifts you one level up: the TCP connection, the HTTP request format, and header parsing all vanish behind `urlopen()`. BeautifulSoup then lifts you above the HTML syntax layer — instead of matching angle brackets with regex, you navigate a tree. Each layer buys you simplicity at the cost of control, which is exactly the same tradeoff made at every layer of the Internet stack. The web services half of the day reinforced the same point: JSON is just Python dicts and lists serialised as text, which is why `json.loads()` returns native structures requiring no further special handling — the entire parsing job collapses to one line.

**Networking:** The most striking thing about Section 2.2 is how much of the Web's design is the result of deliberate tradeoffs rather than accidents. Statelessness was a choice — it makes servers simpler to scale but forces cookies as a retrofit. Non-persistent connections were a choice — they make implementation simple but waste RTTs, which is why HTTP/1.1 reversed the default. Caching was a choice to solve a real bottleneck: the quantitative example makes the point vividly — a 15 Mbps link at 100% utilisation collapses under infinite queuing delay, but a cheap proxy cache with a 40% hit rate reduces that load to 60% and brings average response time to 1.2 seconds, at a fraction of the cost of a link upgrade. Every major HTTP feature — persistent connections, pipelining, conditional GET, cookies — is a targeted solution to a concrete performance or usability problem introduced by the one before it.

## Problems I Encountered

### Python — Networked Programs

**Confusion #1: `recv()` doesn't always give you the full `n` bytes** **Problem:** Called `recv(5120)` and sometimes got back 3200 bytes, sometimes 5120, inconsistently. Expected a fixed chunk size every time. **Resolution:** `recv(n)` returns _at most_ `n` bytes — however many have arrived so far. The network delivers data in variable-sized chunks depending on speed and buffering. To get consistent full-sized chunks, add `time.sleep(0.25)` so the buffer has time to fill. This is TCP flow control at work — the sender pauses when the receiver's buffer is full.

**Confusion #2: Forgetting the blank line at the end of the HTTP request** **Problem:** Sent `GET http://data.pr4e.org/romeo.txt HTTP/1.0\r\n` to the socket — server appeared to hang and never responded. **Resolution:** HTTP requires a blank line (`\r\n`) after the headers to signal end of request. Without it, the server keeps waiting for more headers. The correct terminator is `\r\n\r\n` — two CRLF sequences in a row.

**Confusion #3: Regex on real HTML is fragile** **Problem:** Used `re.findall(b'href="(http[s]?://.*?)"', html)` — worked fine on simple test pages, missed several valid links on real-world pages where `href` had single quotes, uppercase, or extra whitespace. **Resolution:** Regex matches exact character patterns; real HTML is inconsistent. For any HTML that came from the real web, BeautifulSoup is more reliable because it builds a proper parse tree rather than pattern-matching text.

### Python — Web Services

**Confusion #4: `findall` path must include all parent elements except the root** **Problem:** Called `stuff.findall('user')` expecting to find user nodes — got back an empty list. **Resolution:** `findall` looks for elements matching the path as _direct children_ of the element it is called on. Since `user` is a child of `users`, which is a child of `stuff`, the correct path is `'users/user'`. The root element (`stuff`) itself is omitted — everything below it must be specified.

**Confusion #5: `.find()` vs `.findall()` return types** **Problem:** Tried to loop over the result of `.find('name')` — got `TypeError: 'Element' object is not iterable`. **Resolution:** `.find()` returns a single `Element` object (or `None`). `.findall()` returns a Python list. Use `.find()` when you want one element; use `.findall()` when you need to iterate over multiple matches.

**Confusion #6: Calling `.text` on a missing element** **Problem:** `tree.find('missingTag').text` threw `AttributeError: 'NoneType' object has no attribute 'text'`. **Resolution:** When `.find()` doesn't match anything it returns `None`, not an empty element. Always guard: `el = tree.find('tag'); val = el.text if el is not None else 'default'`.

**Confusion #7: `json.load()` vs `json.loads()`** **Problem:** Passed a string from `urllib` to `json.load()` — got `AttributeError: 'str' object has no attribute 'read'`. **Resolution:** `json.load()` takes a _file handle_ (something with a `.read()` method). `json.loads()` takes a _string_ or bytes object. When you have the raw response from `urllib`, use `json.loads()`.

### Networking

**Confusion #8: Why does non-persistent HTTP cost 2 RTTs and not 1?** **Problem:** Expected the HTTP GET and response to cost 1 RTT. Didn't understand where the second one went. **Resolution:** The first RTT is the TCP three-way handshake — client sends SYN, server replies SYN-ACK, client sends ACK (which is combined with the HTTP request). Only after this handshake is the TCP connection established. The second RTT is the HTTP request travelling to the server and the first bytes of the response arriving back. The file transmission time is then added on top of both RTTs.

**Confusion #9: Why can't the server just remember who I am between requests if HTTP is over TCP?** **Problem:** TCP is a persistent connection (in HTTP/1.1) — so why doesn't the server know it's the same client on the second request? **Resolution:** TCP and HTTP are different layers. HTTP statelessness is a _protocol design choice_ at the application layer, independent of what TCP does at the transport layer. Even on a persistent TCP connection, the HTTP protocol itself carries no session identity — the server processes each request as if it arrived fresh. State must be explicitly layered back on top using cookies or session tokens.

**Confusion #10: If the cache's hit rate is only 40%, how is it actually saving much?** **Problem:** 40% seemed low — I expected caching to only help if it was hitting most of the time. **Resolution:** The benefit isn't proportional to hit rate in the way I expected. The key metric is _traffic intensity on the access link_, not the hit rate itself. Reducing the load on a near-saturated link from 100% to 60% is the difference between infinite queuing delay and manageable queuing delay. The relationship between traffic intensity and delay is non-linear — near 1.0, delay explodes. Dropping utilisation from 1.0 to 0.6 is disproportionately valuable.

**Confusion #11: What is the `304 Not Modified` response actually saving?** **Problem:** The conditional GET still involves a round trip to the server — isn't that as slow as just fetching the object again? **Resolution:** The saving is _bandwidth_, not _round trips_. A `304` response has an empty body — no object bytes are transmitted. For large objects (images, videos, scripts), that's the expensive part. The round trip cost (propagation delay) is paid either way, but re-downloading a 500 KB image when it hasn't changed is wasteful. The conditional GET confirms freshness cheaply and lets the cache serve the already-stored copy.

**Confusion #12: Does HTTPS break caching entirely?** **Problem:** If traffic is encrypted end-to-end, a proxy cache can't read or cache the content — so how do CDNs work with HTTPS? **Resolution:** This is one of my open questions from the notes. The short answer is that CDN nodes act as TLS _termination points_ — the TLS session ends at the CDN server, which decrypts the content, caches it, then re-encrypts it for delivery to the client. The CDN effectively acts as a trusted intermediary rather than a transparent proxy. This works because the content owner (e.g., Netflix) configures their CDN deliberately, unlike a third-party ISP proxy that has no business decrypting your traffic. A standard ISP-level proxy cannot cache HTTPS content for this reason.

### Networking — Cookie Lifecycle

```
First visit (no cookie):
  Browser → GET /  →  Server
  Server creates ID 1678 in database
  Server → HTTP 200 + Set-cookie: 1678  →  Browser
  Browser stores: amazon.com → 1678

All subsequent visits:
  Browser → GET / + Cookie: 1678  →  Server
  Server looks up 1678 → personalised response
```

### Networking — Web Cache Performance

```
No cache (15 Mbps link, 15 Mbps demand):
  Traffic intensity = 15/15 = 1.0 → queuing delay → ∞

100 Mbps link upgrade:
  Traffic intensity = 15/100 = 0.15 → ~2 s (Internet delay dominates)
  Cost: expensive leased line upgrade

Local cache (hit rate = 0.4, same 15 Mbps access link):
  Effective load on access link = 0.6 × 15 Mbps
  Traffic intensity = 9/15 = 0.6 → small queuing delay
  Avg delay = 0.4 × 0 s + 0.6 × 2 s = 1.2 s
  Cost: inexpensive PC + open-source software (e.g. Squid)
```

### Networking — Conditional GET Flow

```
First fetch:
  Cache → GET /object  →  Server
  Server → 200 OK + Last-Modified: [date] + body  →  Cache
  Cache stores: object + Last-Modified date

Later (freshness check):
  Cache → GET /object + If-Modified-Since: [date]  →  Server

  If unchanged:
    Server → 304 Not Modified (empty body)  →  Cache
    Cache serves stored copy to browser

  If changed:
    Server → 200 OK + new Last-Modified + new body  →  Cache
    Cache replaces stored copy; forwards to browser
```
