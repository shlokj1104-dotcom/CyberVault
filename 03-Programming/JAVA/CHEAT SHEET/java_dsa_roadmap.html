The Core Problem
03
Problem 1 · Syntax ≠ DSA
Knowing Java's for loops, ArrayList, and OOP doesn't mean you know data structures and algorithms. DSA is a separate skill — recognizing which structure fits a problem and reasoning about time/space complexity. Java is just the language you express that reasoning in. Don't mistake fluency in one for fluency in the other.
Problem 2 · LeetCode Before Theory
Jumping straight into random LeetCode problems before learning the underlying structure means every "Easy" array problem feels like trial and error. Build the mental model first — how a pointer moves through an array, how a collision is resolved in a hash table — then problems start looking familiar instead of new.
Problem 3 · Sheet-Hopping
Switching between Striver's sheet, a YouTube playlist, and GeeksforGeeks every few weeks because progress feels slow. Pick one sheet, one book, one platform per stage and stay with it until that stage is actually done — not until it feels boring.
Book Verdict
04
Your three books aren't competing for the same job — each owns exactly one stage. Use the reference book to convert Java knowledge into DSA foundations, the intermediate book to turn foundations into interview patterns, and the advanced book once placements stop being the bottleneck.
✅ Data Structures & Algorithms in Java — Lafore (Book 1 · Reference)
Use for: Stage 0–4 foundations. You already know Java syntax, so this book moves fast past setup and spends its time building every classic structure from scratch with full working Java code, not pseudocode. Skip: Ch 1 (Java/OOP review) and Ch 9–10 (Red-Black Trees, 2-3-4 Trees) on a first pass — return to them later if curious.
✅ Cracking the Coding Interview — McDowell (Book 2 · Intermediate)
Use for: Stage 2–6, once foundations are solid. The bridge from "I know what a linked list is" to "I can solve a 30-minute interview problem live, in Java." Skip: Ch 9 (System Design), Ch 11 (Testing), Ch 14 (Databases) — not relevant to DSA-focused campus placements yet.
⚠️ Algorithms, 4th Ed — Sedgewick & Wayne (Book 3 · Advanced)
Use for: Stage 4–6, once BFS/DFS and basic sorting are second nature. Written entirely in Java with a free companion course. Unique value: rigorous Union-Find, balanced trees, and graph algorithms with real proofs. Skip now: Ch 6 "Context" (B-trees, suffix arrays, max-flow, intractability) until well past placement-level DSA.
❌ What's Genuinely Missing
None of your three books are a problem-bank — they teach structures, not interview pattern recognition at scale. You need a sheet (Striver's A2Z) and a platform (LeetCode) running in parallel from Stage 0 onward. See the Practice Arena tab.

Java Tool Cheat-Sheet
02
Linear Structures
ArrayList<T>
Dynamic array, O(1) amortized append, O(n) insert/delete in the middle. Your default choice for "just store a list of things."
LinkedList<T>
Implements both List and Deque. Rarely beats ArrayList in practice — matters when a problem explicitly needs O(1) insert/delete at a known node.
ArrayDeque<T>
Preferred over Stack and LinkedList for both stack and queue use. Faster, no legacy synchronization overhead.
Stack<T>
Legacy class from Java 1.0. Works fine, but ArrayDeque is the modern idiomatic choice unless a problem expects the Stack API specifically.
Hashing & Sets
HashMap<K,V>
O(1) average lookup/insert. The single most-used data structure in interview solutions — when stuck, ask "can a HashMap make this faster?"
HashSet<T>
O(1) membership check. Use for "have I seen this before" patterns.
TreeMap / TreeSet
Sorted key order, O(log n) operations. Use when you need ordering plus lookup — "closest value," "next greater key."
LinkedHashMap<K,V>
Preserves insertion order. The standard building block for an LRU cache implementation.
Trees, Heaps & Graphs
PriorityQueue<T>
Min-heap by default. Pass a Comparator for a max-heap or any custom ordering.
Custom Node<T>
For binary trees, BSTs, and linked lists, you write these yourself — Java has no built-in tree class.
List<List<Integer>>
The standard adjacency-list representation for a graph.
boolean[] visited
The essential companion to every BFS and DFS you'll ever write.

Mini Projects To Cement Each Stage
04
Custom Generic ArrayList
Build your own MyArrayList<T> backed by a raw Object[], implementing add/get/remove/resize. Watch what happens to performance when you forget to double the capacity on resize. Stage 1 project.
LRU Cache — Twice
First implement it using only LinkedHashMap (5 lines). Then implement it again from scratch using a HashMap + a hand-built doubly linked list. Comparing the two is exactly how interviewers test whether you understand what the built-in does for you. Stage 2–3 project.
Word Search Autocomplete (Trie)
Build a Trie supporting insert(word) and a getSuggestions(prefix) method returning all matching words, sorted. This is the actual data structure behind every autocomplete you've used. Stage 3 project.
Maze Pathfinder (Grid BFS/DFS)
Take a 2D char grid (# wall, . open), find the shortest path from start to end using BFS, then count total reachable cells using DFS. Print the grid with the path marked. Stage 4 project.

How To Actually Use LeetCode
03
LeetCode is a tool, not a scoreboard. Rating-chasing and streak-collecting are distractions — the goal is pattern recognition, not a green calendar.
The 25-Minute Rule
Set a 25-minute timer. If you haven't found the approach, look at a hint — not the solution. If you're still stuck, read the solution, understand it fully, close it, and re-write it yourself from a blank file.
The Pattern Tag
After solving, write one line: "this is a sliding-window problem because ___." That sentence is what transfers to a new problem with different surface details — the code itself doesn't.
The Revisit Rule
Mark every problem you struggled with. Revisit it after 3 days, then after 2 weeks. If you can solve it cold both times, the pattern is actually yours — not just memorized.
The No-Copy Rule
Never copy-paste a solution — not from a forum, not from your own old code. Type it out by hand every time. Typing engages a different kind of memory than reading does.

Five Unbreakable Rules
02
Foundation Rules
Rule 1: Don't touch Graphs or DP until Stage 2 (Linked List/Stack/Queue/Hashing) is fully done.Most learners skip ahead and get stuck because recursion and hashing aren't automatic yet.
Rule 2: Always write the brute-force solution first, even when you already know a better one.Understanding why the brute force is slow is what teaches you to recognize the optimization next time.
Rule 3: One sheet at a time. Pick Striver's A2Z sheet as your single source of "what to solve next."Don't also run NeetCode 150 or GFG 160 simultaneously — finish one before starting another.
Rule 4: Re-solve any problem you couldn't crack in 25 minutes, 3 days later, without looking at your old solution.If you can't redo it cold, you memorized the answer, not the pattern.
Practice Rules
Rule 5: Every topic needs at least 15 problems solved on that exact topic before you move on.Theory without volume practice doesn't build real pattern recognition.
DSA Rule: Log every problem in your Obsidian vault — pattern used, time taken, mistake made.Review the log weekly, not just when you remember to.
Contest Rule: Once Stage 4 is done, do at least one Codeforces Div 3/4 contest every 2 weeks.Even solving only 1–2 problems builds speed under pressure that untimed practice never will.
Java Rule: Use java.util classes for actually solving problems — only hand-build a structure once, for learning.Interviewers want correct, idiomatic Java, not a reinvented wheel.
